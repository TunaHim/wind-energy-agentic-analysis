How the data pipeline works

This page covers the data and software side of the North Sea wind prototype. It shows how km-scale EERIE climate-model output is read straight from the DKRZ cloud and cut down to the North Sea. That cut-out becomes a 1.75 MB Parquet package, which is everything the live app and its agent ever read.

1. The pipeline at a glance

Data flows from left to right. Each box is one stage, and the blue text names the code that does it. The first three stages run once on a workstation. Only the last two run in the deployed app.

2. Why so much is read and so little is kept

The EERIE daily output is stored on the model's native reduced Gaussian grid as one flat array of 6,599,680 points per day. Each stored chunk holds two days of the whole globe. Whatever region you want, each chunk has to come over the network in full.

Because the cost of each request is known in advance, estimate_native_transfer_gb() can work out the transfer volume before a download starts.

3. Problems the pipeline had to solve

native grid

No regular lat/lon grid

The native grid is one long list of points, not a rectangle, so a box cannot be sliced by index ranges. The lat and lon arrays are read once from the store, and the indices of the points inside the box are kept and reused for every chunk.

longitudes

0–360° versus −5°E

EERIE stores longitudes from 0 to 360°. They are converted to −180…180° before masking, so a western bound like −5°E selects the right points instead of nothing.

direct chunk access

Fetch only the chunks needed

Chunk numbers are worked out from the wanted dates (days since 1 January 2015, divided by two). Each chunk is fetched by URL and decoded with Blosc, so the build reads exactly the chunks it needs and nothing else.

reliability

Large, slow transfers

Every request has a 15-minute time-out and up to six retries with growing waits. The five variables of a chunk are downloaded in parallel. Each finished chunk is saved straight away, so a restart continues where it stopped.

deployment

A free cloud host

Streamlit Community Cloud cannot hold or stream gigabytes. A separate build step reduces the data to five small files per month. The app checks that the package is complete before it starts and stops with a clear message if it is not.

secrets

API keys stay out of git

LLM keys are read from Streamlit secrets or environment variables. If no key is set, or a model returns an invalid tool call, the user is pointed to the built-in agent, which needs no network.

provenance

Every file says where it came from

Each build writes a manifest with the dataset URL, box, variables, periods, row counts, dates and mask status. The agent has a provenance tool that returns this record with any answer.

honesty

Limits stated, not hidden

The data hold 10 m wind only, so every hub-height number uses an explicit power-law exponent the user can change. The agent has tools that check screening readiness and explain limitations, and the mask is labelled preliminary.

6. In one sentence

Km-scale climate-model output is read from a public cloud Zarr archive chunk by chunk, with the cost known in advance and every transfer retried and resumable. It is cut to the North Sea in memory and stored as Parquet with a manifest, then reduced to a 1.75 MB package. A web app and a tool-bounded AI agent answer questions from that package alone, always with their provenance and limitations.
